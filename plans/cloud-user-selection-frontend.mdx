# Cloud User Selection Frontend LLD

## Objective

Render a development-only, user-selected action inbox in the existing compact 380×520 Cloud window. Full-size or dashboard UI is intentionally deferred.

## API boundary and models

Extend `frontend/src/shared/api/cloudGateway/` with Cloud-direct TypeScript models and gateway client methods for:

- `UserListResponse` / `CloudUser` from `GET /v1/dev/users`;
- `ActionListResponse` / `Action` from `GET /v1/actions`;
- `OverviewResponse` from `GET /v1/overview`.

Every method derives its URL from the existing Gear6 backend origin and uses `/api/cloud/*`. Actor-scoped methods carry `account_id` as a query parameter only; they never emit `X-G6-Actor-ID`.

## Component design

`CloudRoot` remains responsible for readiness and its recoverable failure states. Once readiness succeeds:

- production builds keep the existing ready surface and make no user, actions, or overview request;
- development builds mount `CloudInbox`.

`CloudInbox` owns the following local, session-only state:

| State | Initial value | Behavior |
| --- | --- | --- |
| users | loading | populated from the development user directory |
| selected account | first returned user | changes only through the selector; never persisted |
| inbox | loading | actions and overview for the selected account |
| request version | zero | increments on user change; old responses are ignored |

The selector is a native labelled `<select>` so it is keyboard-operable without a custom popover or focus trap. User display falls back from display name to handle to account ID.

## Compact visual behavior

- Keep the existing transparent, always-on-top window and its 320px minimum width unchanged.
- Use existing theme tokens and Inter; do not introduce a separate visual system.
- Render a product header, small development marker, selected-user control, total/open-for-you summary, an updated label, and compact status chips.
- Each row displays action category/audience, action age, source subject, fixed API instruction, and optional entity summary. Never fabricate source messages, people, or channel context.
- Clamp variable strings to prevent horizontal overflow; separate rows with the shared `Separator` component.
- Display explicit loading, empty, and error states for user discovery and selected-user reads.

## Request lifecycle

1. On development mount, fetch users once.
2. Select the first returned account (or render the empty selector state when none exist).
3. On every valid selection, concurrently request actions and overview.
4. Associate both responses with the current monotonically increasing request version.
5. Commit a response only if its version still equals the latest selection; a slower prior selection cannot overwrite the current inbox.

## Test plan

- Client tests assert backend-only origins, development route paths, `account_id` query creation, and no browser actor header.
- Root tests assert the selector/API work is excluded from non-development builds.
- Component tests cover first-user selection, user switching, loading, empty, failure, row truncation, accessible selector labelling, and stale-response suppression.
- Compact-width visual smoke test verifies the 320px layout remains readable and scrolls only within intended content areas.
